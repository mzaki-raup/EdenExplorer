| Completed | **Additional network discovery protocols** — mDNS and WS-Discovery, two more ways for "Shared Network" to find devices that don't announce over legacy NetBIOS browsing (the sidebar's existing `enumerate_network_level`/`scan_local_subnet` discovery). Both are hand-rolled with **zero new dependencies** (matching this module's existing style - it already hand-rolls raw NBSTAT parsing and Win32 WNet browsing rather than reaching for a crate), sending one query and listening briefly for replies: `core/network_mdns.rs` sends a `PTR _smb._tcp.local.` mDNS query with the unicast-response (QU) bit set (so replies come straight back to our own ephemeral port - no need to bind port 5353 or join the multicast group ourselves, which could conflict with a real mDNS responder already on the machine), then chains PTR -> SRV -> A through a small hand-rolled DNS-message reader (with `0xC0` compression-pointer following, since NBSTAT parsing didn't need that) to resolve each responder's IPv4. `core/network_wsd.rs` sends one WS-Discovery `Probe` (a small SOAP/XML template, `quick-xml` - already a dependency, used today by the PDF/DOCX preview extractor - parses the `ProbeMatch` replies) to the WS-Discovery multicast address and reads whichever IP comes back in `wsd:XAddrs` (falling back to the reply packet's own source address). Both modules only return candidate IPv4s, not `NetworkComputer`s - `network.rs`'s `discover_network_computers()` runs every candidate through the *same* SMB-port-445 verification and NetBIOS name resolution the existing subnet sweep already uses (a new shared `has_smb_open` helper, extracted from `probe_smb_host`'s inline check), so a device that merely answers mDNS/WSD but doesn't actually serve SMB - a printer answering WS-Discovery, say - never shows up in "Shared Network" faking a browsable share. **Bundled fix:** `get_network_computers_cached()`'s background rescan never called `request_repaint()` after refreshing its cache (confirmed - unlike every other background-thread feature in this codebase, which all wake the UI this way), so a fully idle window could sit on a stale device list; added the missing call, which matters more now that the scan can take noticeably longer (two ~1.5-2s multicast round-trips). 5 new unit tests (hand-built valid mDNS response and WS-Discovery XML fixtures, plus malformed-input cases) verify both parsers in isolation. Live-verified: built clean in both debug and release with no `Cargo.toml`/`Cargo.lock` changes, ran on this machine's real LAN with temporary debug logging (removed before done) confirming both new discovery calls execute without error and return gracefully (empty, on this particular network - no mDNS/WSD responder present here to positively trigger the match path, but the existing NetBIOS/subnet-sweep hosts still appeared unregressed in the sidebar throughout). |
