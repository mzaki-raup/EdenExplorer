| Completed | **Fixed: `.exe`/`.dll`/`.ico`/`.lnk`/`.scr`/`.cpl` files showed a wrong or missing icon** — user report: "some of icon for exe file not showing." Root cause: `icon_key` (`gui/icons.rs`) cached every non-directory file's icon purely by extension (`ext:exe`), and the lookup for that key asked the shell for the icon of a fake, nonexistent `file.exe` via `SHGFI_USEFILEATTRIBUTES` — which works for extensions with one shared, registry-associated default icon (`.txt`, `.pdf`, ...), but a `.exe`'s (or `.dll`/`.ico`/`.lnk`/`.scr`/`.cpl`'s) real icon comes from that specific file's own embedded resources, not a registry-wide default, so the fake-file lookup could return nothing useful and every file sharing that extension was stuck showing whichever result got cached first. | Completed | **Fixed: copying/moving a file into the other pane in dual-pane view snapped the active pane back to the first pane instead of staying on the one just interacted with** — user report: "when I copy file/folder to second pane, when finished, it back to first pane." Root-caused two separate, compounding bugs, not one: (1) `self.focused_split` is only ever set by a primary-*click*, and a drag-and-drop's initial press fires in the *source* pane (where the drag started), not the *destination* pane it's dropped onto - so dropping a file into the other pane never actually made that pane the active one in the first place, even before anything async ran. Compounding this, `mainwindow.rs`'s per-frame routing of `pending_action`/`secondary_pending_action` (which temporarily flips `self.focused_split` to whichever pane's UI produced an action, purely so shared handlers can resolve via it, then explicitly restores the *prior* focus afterward) restored focus back to the source pane immediately after handling the drop - even for a real, deliberate interaction like a drag-and-drop that should reasonably make the destination pane "active" going forward. (2) Separately, `poll_pending_paste`'s completion handler (once the async robocopy job actually finishes) called `self.load_path()` - which reloads whichever pane is *currently* focused - instead of reloading `pending.side`, the pane the paste actually targeted; those two can differ by the time a job finishes. Fixed by (1) tracking whether the routed action was a real drag-and-drop (`ItemViewerAction::MoveItems`) for either pane, and if so, leaving `self.focused_split` on that pane instead of restoring the prior one - matching standard dual-pane file manager behavior (Total Commander, etc.) where dropping into the other pane makes it active; and (2) changing the paste-completion reload to `self.load_view(pending.side)`. `cargo test` (114/114) passes; no i18n changes. **Verification note**: the fix is a direct, mechanically-traced correction of two confirmed root causes (not a guess), and build/tests pass clean, but live re-verification via a real cross-pane drag-and-drop was not completed - this environment's synthetic-input tooling (`PostMessage`-based mouse-down/move/up) could not reliably get egui to recognize a cross-pane drag-and-drop as a real drag rather than a plain click on the source row, across several retries with progressively finer-grained movement steps. This is a new limitation of the test harness worth remembering for next time a drag-and-drop-specific fix needs live verification. **Follow-up (user reported the same class of bug again, from a different trigger): "when I copy file/folder from other folder to second pane, when click replace button, it focus to first pane."** The previous fix only covered `ItemViewerAction::MoveItems` (drag-and-drop); a clipboard/context-menu Paste that hits a name conflict routes through `ItemViewerContextAction::Paste` instead, which the previous fix's `primary_drop`/`secondary_drop` check didn't match - so Paste-with-conflict still fell through to the old restore-to-prior-focus behavior. But tracing this precisely surfaced a second, more fundamental cause specific to the Replace/Skip/Rename modal: that modal is drawn as an `egui::Area` anchored to the **whole window's** center, not either pane's - so one of its own buttons (Replace, being part of a right-aligned cluster) can sit at a screen position that geometrically overlaps `primary_rect` purely by coincidence of where the window's horizontal center happens to fall relative to the two panes. `mainwindow.rs`'s raw pointer-position pane-focus detector (`if primary_clicked { if primary_rect.contains(pos) {...} }`) runs unconditionally every single frame reading raw click coordinates, with no awareness that a modal button consumed the click on top of it - so clicking Replace reassigned `focused_split` back to whichever pane the button's coordinates happened to overlap, independent of anything the paste itself did. Fixed both causes: (1) generalized the previous fix from "keep focus only for `MoveItems`" to "any pane whose own widgets produced a real action this frame keeps focus" (removed the `primary_drop`/`secondary_drop` special-casing entirely - by construction, every `pending_action`/`secondary_pending_action` already represents a deliberate interaction with that specific pane, so restoring prior focus after handling one was never actually correct for any of them, not just drag-and-drop); (2) guarded the raw click-position pane-focus detector with the same `blocking_modal_open` check (`pending_paste_conflict`/`pending_bulk_rename`/`pending_checksum`) this codebase's own `BLOCKING_MODAL_MEMORY_ID` mechanism already uses elsewhere to stop a modal's own clicks from leaking through to whatever's visually underneath it - this is a second, independent instance of that same general class of bug (a modal visually on top doesn't automatically suppress unrelated per-frame input handling below it), just hitting pane-focus detection instead of keyboard shortcuts this time. `cargo test` (114/114) passes; no i18n changes. **Verification note**: build/tests pass and both fixes are traced precisely to confirmed mechanisms (not guesses) - the geometric-overlap theory for the modal specifically explains why *Replace* (not just any click) was implicated - but live re-verification was not completed this session; the test window couldn't be brought to the foreground across several retries (the user appeared to be actively at the keyboard elsewhere the whole time), so driving it further was skipped rather than risk interfering, per this file's own "the user might be in the same window" gotcha. |
